Automatic backups start only in these hours, on the server's clock; the same hour twice means any time. If the app was not running then, the notifications ask what to do. A consistent copy of the library as it was when the backup started, made in the background while you keep working, and written to data/<user>/backups/. It covers the database only: characters, chats, lorebooks, settings. Images, avatars and gallery media are ordinary files on disk and are not included. The database is the part that changes constantly and the part worth copying often, which is what this does. It is not a substitute for copying the whole data/ folder now and then: restoring a database on its own leaves the images as they are today, so anything imported since the backup keeps its files while losing its entry, and anything deleted since comes back without its picture.
Existing backups
How to restore one

There is no restore button yet. It is done by hand, and the third step is the one that matters.

  1. Stop the app. Copying over a database that is still open is how you damage it.
  2. In data/<user>/, rename library.db to something else. Keep it. If the restore is not what you wanted, it is the only way back.
  3. Copy the backup from backups/ into its place and rename it to library.db. Then delete library.db-wal and library.db-shm if they are there. They belong to the old database, and leaving them lets it write itself back over the one you just restored.
  4. Start the app and check the character count above looks right.

Images are not part of this. Characters imported since the backup will keep their picture files while losing their entry, and characters deleted since will come back without a picture. Running npm run verify lists anything whose image is missing.

Hosted Browser
Browser
Some sites are only reachable from a real browser: Cloudflare challenges everything else, and passing that challenge earns a cf_clearance cookie no server-side request can hold. Project Σ can run and manage that browser for you, or drive one you host yourself. Every provider that needs one shares it; today those are JanitorAI and JannyAI, and each one's section below has a Check that says whether the browser gets through to its site.
A hidden browser starts on the machine running Project Σ, the first time something actually needs it, and shuts itself down after 10 minutes idle. Whether it gets past Cloudflare depends on the machine, so press Test to find out instead of assuming: a headless server or single-board computer can work (measured on an ARM board, software rendering included). On a shared server only the owner can use it; other accounts point the endpoint setting at a browser they run themselves.
Not started

JanitorAI Beta
Step 1: Browser
Required. JanitorAI is only reachable from a real browser, so this provider is built around the Hosted Browser configured above. Nothing else here works until that does, including signing in. Press Check to see whether that browser gets past janitorai.com's Cloudflare.
The browser does two jobs here. Cloudflare: janitorai.com challenges everything that is not a real browser, and passing it earns a cf_clearance cookie that only a browser can hold, so no server-side request ever gets through on its own. Hidden definitions: around half of all characters withhold theirs (the field is absent from the API) and the only way to see one is to let JanitorAI build a chat prompt and read it back.
Use a throwaway JanitorAI account. Recovering a definition briefly points that account's API settings at a dummy preset and opens a chat, then puts everything back. It is tidy, but it is still your live account.
Step 2: Account Login
Also required. The browser gets you to JanitorAI; an account gets you the content. Without one you see the first page of results and nothing else: no follows, and no character extraction, which is the only way to recover a hidden definition. Sign in here rather than on the site, since the login runs through the browser above. The session refreshes itself, so you should rarely repeat this, though signing in to JanitorAI elsewhere can end it. Your email, password and session are saved server-side against your account, not just in this browser.

Bring your SillyTavern library

Cards with their tags and favorites, chats, lorebooks and their links, gallery media, version snapshots, playlists, personas, custom CSS, saved prompts and filter presets come across. The folder is only ever read, and re-running is always safe until you finalize: every character heals in place and nothing duplicates.

Coming from the Character Library extension?

SillyTavern keeps one gallery folder per character name, while Project Σ gives every character its own gallery, so characters that share a name each come across with a full copy of that folder. Nothing is lost, the images are just duplicated. To avoid it, in the extension:

  1. Open its Gallery Folders settings and turn on Use unique gallery folder names.
  2. Press Assign Gallery IDs.
  3. Press Smart Relocate. It fingerprints each character's online gallery and embedded media, then moves every matching image into its owner's own folder.

What does not come across
  • Group chats and group definitions. They are counted in the plan and stay at the source.
  • Character Library extension settings: provider logins, view preferences, every other extension option. Configure Project Σ fresh.
  • SillyTavern's own settings: API connections, sampler presets, themes, Quick Replies, instruct and context templates. Chat-completion prompt presets can be imported inside the Prompt Manager.
  • Tags applied through SillyTavern's tag manager. Those live in its settings, not on the cards; only tags embedded in the cards migrate.
  • Chat backgrounds, expression sprites and other SillyTavern asset folders.
